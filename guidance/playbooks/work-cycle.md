# General work cycle

Use this for substantive or multi-step work of any kind: research, writing, data, design, software, external services or scheduled work. This is the single general execution and closure procedure; methods and host capabilities own their specific techniques. These are responsibilities, not mandatory conversation rounds. A simple answer or small edit can finish directly without a plan, project record, delegation or development checks.

Use referenced guidance through the configured route and applicable consumer pin. A missing procedure or tool is an explicit limit; do not silently import a newer version or claim unavailable work was performed.

## 1. Establish the requested result

Identify the outcome, scope, existing permission and intended destination. Reuse accepted decisions. Distinguish an explanation, proposal, implementation and publication by what the user actually requested; a method adds no authority. Choose routine reversible details from evidence, but do not invent missing facts, domain rules or consequential user decisions.

Follow `context-entry` for the relevant sources, owners, versions and current state. Resolve available facts before asking; ask only when an unresolved choice materially changes the action, destination or acceptance. Prepare independent work so a necessary decision concerns a concrete result. Finish with an observable acceptance condition and its actual owner, or the precise missing fact.

## 2. Choose a proportionate route

Use the configured method router to select one primary procedure when needed. Direct answers and host-capability-only operations are valid routes. Load the selected method and only relevant roles/references; names or installation alone do not establish use. Use the supported artifact, app, data or scheduling capability for the requested output. Do not route non-software work through development merely to give it a method.

For a decisive uncertainty, perform a bounded investigation, diagnosis or prototype, then return to the requested outcome. For multiple results, order genuine dependencies and retain one coherent assignment. Finish when the next action, evidence needed and permitted effects are clear; complete discovery of every possible later choice is unnecessary.

## 3. Execute ready work

Carry out all ready authorized work in usable steps. A new session, method, agent or status question does not revoke existing permission or end the assignment. Incorporate new instructions; answer status questions briefly and continue unless the user changes or stops the goal. A blocker pauses only dependent work; continue independent parts without prejudging the blocked decision.

Apply `context-entry` freshness rules before changing shared destinations. Preserve unrelated work and use revision checks where available. If an action may have succeeded, inspect its exact target before retrying; an absent response is not proof of failure. Use the selected `interruption-recovery` procedure after an interruption, preserving the last proven state and first unproven action.

Use useful authorized delegation through the selected `delegation` playbook; the parent retains decisions and integration. A separate workspace does not isolate shared external objects. Without delegation support, continue the supported task without claiming independent review.

External writes, publication and irreversible effects follow the actual task authority and tool limits, without an extra blanket approval round. Sending to others requires an explicit sending instruction. For future or recurring work, use an actual scheduling capability: check relevant existing tasks, resolve trigger, relevant time/timezone, scope and destination, and verify registration. Bound retries and state when a run needs input or must stop. A chat promise or temporary agent is not a schedule.

## 4. Verify and repair the result

Check both requested acceptance and applicable quality: factual support, preserved content and user choices, usable output, and relevant failure/recovery behavior. Match evidence to the claim and exact resulting state, including unsaved or uncommitted changes when relevant. Use independent review when it materially improves assurance, not as a universal gate. Read findings, repair valid issues within scope and repeat checks affected by the repair or new evidence.

| Result | Evidence needed for the claim |
| --- | --- |
| Research or advice | Relevant primary sources and dates/versions; supported conclusion separated from interpretation and uncertainty |
| Text, document or presentation | Content, references and important figures checked; final rendered output inspected where layout/readability matters |
| Data, spreadsheet or conversion | Traceable input, units, formulas, counts and relevant edge cases; a discriminating independent check where needed |
| Software | Requirements and quality review of the actual change; applicable tests/build and runtime evidence for runtime claims |
| Interface, image or design | Inspectable requested output; visual or interaction evidence appropriate to the claim; precise data represented with suitable exact tools |
| External operation | Correct object/recipient/destination and system evidence of the requested effect; readback when uncertain or required |
| Scheduled work | Actual task identifier and configured trigger, relevant time/timezone, scope and destination; a completed run claimed only after observed execution |
| Learning | Explanation/example appropriate to the request; demonstrated understanding only when observed, with no forced quiz for a direct explanation |

Structural checks, simulations, runtime observations, rendered inspection and publication each prove different things. Green checks do not erase unmet acceptance. Do not impose CI, test volume or universal thresholds on unrelated work. Preserve valid evidence until a relevant change invalidates it. Finish with supported acceptance or an exact remaining limitation.

## 5. Deliver and reconcile the existing owners

Provide the usable result or its actual link. Verify required saves and external effects before claiming them. Update changed outcomes, decisions and task status at their established owners, then only affected navigation summaries under `context-entry`. Map meaning to existing statuses; do not create another tracker, ledger or status scheme. Mark the whole assignment complete only when all requested acceptance is supported; partial results can be complete while their parent remains blocked.

For repository changes, additionally follow applicable repository closure and the selected `change-closure` playbook for change-induced residue. Follow actual merge, release or distribution requirements only when relevant and authorized. A draft, saved file, reviewed change, installation, publication and successful run are distinct outcomes.

Keep durable records only where needed for substantive work, decisions or continuation, using the existing task/document owner. Retain scope, owner/source revision, material decisions, evidence limits, uncertain actions and the first unproven next step; link evidence rather than copying full histories. A simple question ends with its answer. Report unresolved access/save failures and the dependent step clearly rather than claiming complete persistence or coverage.

Route recurring instruction friction to `instruction-feedback-loop`. Repair within the authorized scope or preserve the concrete observation at its existing owner; it does not replace the user's priorities. Close with the result, material evidence and any genuine remaining action, not a new maintenance campaign.
