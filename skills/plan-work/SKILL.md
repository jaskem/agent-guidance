# Plan work

## 1. Recover the intended outcome

Follow the user's configured operating guide once per session, including its required tool-call version. Reuse verified context; load project and task owners only when relevant, refreshing them after a project/scope change or material new evidence. Use the routed context-entry playbook when available. If required context is inaccessible, disclose the gap and continue only independent work.

Use available agents without waiting for an explicit user request when this method calls for independent fact-finding or when a bounded parallel task or separate check would improve the result. Follow the routed delegation procedure; give each worker a source/revision, scope, allowed actions and expected evidence. Keep one writer per shared object, use the current host capabilities and let the parent verify and integrate the result. If delegation is unavailable, continue supported work and state any required independence that remains unproven.

Read the current request, applicable project router and existing central plan or task. Resolve current facts from their owner before asking the user. Identify desired behavior, accepted decisions, scope limits and evidence still missing. Notion may own tasks or decisions; verify the ownership map rather than treating every Notion record as secondary. Treat memory and derived summaries as pointers until their source confirms them.

Distinguish planning-only from authorized execution. This method does not grant implementation, publication or scheduling permission. A clear small task can proceed through its existing execution route without a new specification.

## 2. Resolve only material choices

Separate facts to investigate from decisions the user must make. When direction is genuinely open, compare a few materially different approaches against the user outcome, constraints and assumptions; do not generate alternatives to reopen an accepted direction. Keep already accepted choices. Ask a short question only when an unresolved choice changes behavior, scope, compatibility or meaningful cost; explain the recommended option and consequence. Continue independent work while awaiting an answer. Do not invent an answer or reopen settled questions to complete a template.

For ambiguous domain concepts, use the available domain-modeling method and routed domain role. For a question needing visible interaction or state transitions, use the available prototype method. If either method is unavailable, perform the bounded investigation using existing project instructions and disclose the missing capability only if it limits the result.

## 3. Produce the smallest executable plan

Use [plan and task records](references/records.md). Include the user problem, intended behavior, accepted versus proposed decisions, exclusions, acceptance evidence and unresolved dependencies. Preserve the existing central owner; link supporting evidence instead of creating a competing plan.

For multi-step delivery, split into independently demonstrable or verifiable results. Give each task its consumed inputs or interfaces, produced result, acceptance evidence and only genuine blocking edges. Fold setup into the behavior that needs it rather than inventing isolated scaffolding tickets. Name genuine blockers. For a mechanical cross-cutting migration, use compatible expansion, bounded migrations and removal only after consumers move; do not force an unsafe vertical split. Keep important uncertainty as a named decision, not an invented implementation requirement.

## 4. Check and hand over

Check each accepted requirement maps to a result and observable criterion, including likely failure and recovery cases implied by the request. Check task interfaces agree across the plan and remove needless steps or speculative architecture. Check for circular dependencies, omitted existing constraints and proposals presented as approvals. A plan is ready when the first safe action can be taken and remaining blocked decisions are explicit; complete discovery of every future possibility is unnecessary.

Save at the requested or established destination when authorized. Check an uncertain write outcome before retrying. Report a failed save without claiming persistence. Use the current scope to continue execution or deliver the plan; do not add an artificial session stop or ask again for existing permission.

Read [sources and adaptation](references/sources.md) when maintaining this package.
