# Build a visual narrative

For the web-platform branch, load modern-web-guidance before the dependent technical decision when the output implements an interactive HTML/web narrative. Use its accepted package and relevant guides; retain this method's outcome, project browser policy and real visual/runtime checks. Backend-only, native-only and purely editorial work do not trigger that branch.

## 1. Establish the material and destination

Follow the configured operating guide once per session and reuse accepted context, permissions and the existing source/task owner. Resolve audience, message, required facts, visual identity and requested output. Read the actual source; preserve units, uncertainty, quotations and asset provenance. Record extraction gaps instead of inventing missing evidence. A script may shape cadence; it must not become a substitute factual source.

Choose the modality from the requested experience, loading only its reference. For a specialized film format or production batch, read [narrative formats](references/narrative-formats.md):

| Experience | Procedure |
| --- | --- |
| Reader scrolls through an editorial publication | [Offline editorial HTML](references/editorial-html.md) |
| Presenter or reader advances an explanation | [Web presentation](references/web-presentation.md) |
| Viewer watches a timed film or loop | [Motion video](references/motion-video.md); [product film](references/product-film.md) for a product demonstration or embedded loop |

Use the host's native document or presentation workflow for those requested formats. Keep production app design with its existing UI and implementation route. Use motion-design for interactive product transitions and choreography rather than routing every animated interface through a film workflow. Use design-brand-system only when the requested result includes a reusable identity system, and image-art-direction for a complex image-series sub-result. Resolve a material missing choice only when it changes what can be made; carry out independently supported work meanwhile.

## 2. Design the reader's or viewer's path

Map source claims to sections, steps or timed events. Give each visual an explanatory purpose: comparison, relationship, state change, emphasis or orientation. Distinguish factual evidence, proposed interpretation and illustration. Use exact chart/diagram tools for precise information and the supported image tool for created or edited imagery.

Choose typography, colour, spacing and motion from the content and established identity. Develop a representative composition with real content before scaling the work. Inspect and repair it; reuse accepted direction without imposing additional approval rounds. Preserve object identity and spatial continuity when a narrative carries an object between views. Avoid decorative movement that conceals an absent explanation.

## 3. Build and verify the requested output

Use existing supported capabilities and project tools. Check branch-specific dependencies before promising an export; do not assume a runtime, recording tool, audio service or credentials. Keep facts, narration and presentation state traceable to their respective owners.

Build the actual requested artifact when supported. Follow the configured visual-verification playbook when available. Discover the actual target runtime and the user's preferred accessible environment before selecting a capture or interaction tool. Prefer the relevant authorized remote desktop for a native/user-machine target; use a cloud browser only for its intended web target or a documented fallback. A failed local browser runner does not establish that visual checks are impossible. Record what the chosen surface proves and which target-specific claims remain untested. Inspect final rendered output at the intended dimensions, including meaningful dense states, small-screen readability and transitions. Exercise real controls where interactive; a screenshot cannot prove seeking, navigation or playback. Check technical output separately from content and visual quality. Repair material failures and repeat only affected checks.

## 4. Deliver a usable result

Save the artifact and editable source through the applicable storage workflow, verify the save, and link the actual deliverable at its existing owner. State which rendering, interaction, audio and export checks actually ran. A preview, source file and encoded video are distinct results.

If a required tool or source is unavailable, deliver an independently usable supported part where useful, identify the precise unproven step and keep the requested output visibly incomplete. Never invent an MP4, successful offline check, audio review or publication. Keep distribution evidence outside the reusable package. Read [sources and adaptations](references/sources.md) when maintaining this skill.
