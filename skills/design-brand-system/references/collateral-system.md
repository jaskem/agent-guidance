# A reusable collateral family

Use for a requested set or kit of fixed-format pieces. A single artifact does not require a separate design system project.

## Establish the format

Resolve the requested outputs, dimensions, audience, viewing context and editable source needs before layout. Distinguish a presented deck from a self-contained reading deck; screen delivery, office printing and commercial press are different requirements.

Use actual destination specifications for crops and safe areas. Define units explicitly. Do not treat raster asset pixels, CSS pixels, PDF points, printer dots and physical dimensions as interchangeable.

## Prove the family before cascading

Build the smallest reusable structure that serves the actual set: semantic type/color roles, margins/grid, real logo variants, approved imagery and content slots. Preserve coherent expression across formats without cloning one layout everywhere.

Stress-test representative extremes:
- longest and shortest actual names/headlines;
- dense and sparse content, optional missing images and translations when requested;
- unusually wide or tall approved assets;
- smallest delivered rendering and intended presentation conditions.

Correct the cause of a failure rather than silently dropping required content, changing approved words or shrinking every item. Use targeted edits and preserve the user's own content changes; separate content from rendering when it materially protects that work.

## Make reuse bounded

For each reusable block record what it is, how it is built, behavior where relevant, use/do-not-use and observable checks. Each format points to its current source and inspected examples.

Mark slots according to the actual identity contract:
- Fixed: designated assets, approved literal names or other explicitly fixed choices.
- Flexible: fields the request permits to change, with limits.
- Outside the kit: cases requiring a new proposal or owner decision.

A request outside the kit is a scope decision, not an automatic refusal or permission to publish. Complete independent authorized work, and label an uncovered trial as proposed. A localization request does not imply changing an explicitly locked product name; neither does a generic kit rule prohibit an authorized translation.

## Inspect the real output

Check dimensions, content fit, font availability/embedding as appropriate, clear space, asset variant, image provenance and legibility in each delivered format. Compare the family together and inspect relevant details at usable scale.

Place approved logo files beside their rendered use, including the smallest requested size, to catch clipping, coordinate-space errors, unwanted color inheritance and changed proportions. A file hash or contained bounding box cannot prove visual fidelity. Request a suitable approved variant when the existing one fails; do not redesign the mark incidentally.

A contact sheet helps compare a family but does not replace inspecting individual exports. A viewer is useful only if it improves review: keep controls outside the work, retain the artifact's geometry when toggling guides, and show actual dimensions/zoom. Native-pixel and fit views are not physical print proofs. A screen's physical-size claim needs calibration; verify final page dimensions and use an actual-size print proof where that matters.

For commercial press, obtain the printer's required page boxes, bleed/safe area, color profile, resolution and PDF/export requirements. Do not label a browser PDF press-ready solely because it looks right, assume universal CMYK/raster-resolution values, or impose press preparation on an ordinary screen or office-print document.

Use existing format checks. If adding an automated overflow or font check, prove it detects a known failure, accepts a clean case and reports coverage/errors; do not silently count zero measured artboards as a pass. Bounding boxes do not replace visual review.

Finish with actual exports, editable sources when requested, source pointers and the checks/limits for each. A reusable kit remains tied to the system revision and tested contexts; updates require rechecking the affected examples.
