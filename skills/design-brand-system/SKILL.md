# Design a reusable brand system

## 1. Establish the identity decision and owner

Follow the configured operating guide once per session and its active tool-call version. Reuse accepted context, actual assets and user feedback. Resolve the existing brand/project owner and requested applications; do not create another tracker or replace ownership with a prescribed folder layout.

Determine whether the result is a diagnosis, a proposed new identity, an evolution retaining agreed elements, or a reusable kit applying a settled identity. Preserve the user's chosen scope. A small UI repair uses the UI route; a single deck or document uses its format capability with the existing brand source.

Inventory supplied or observed materials: approved logo variants, fonts and their licenses, tokens, imagery, relevant live surfaces, copy/message and prior decisions. Distinguish stated guidelines from actual application, asset quality from implementation failures, and absent evidence from a defect. Inspect representative materials before judging them. Without a baseline, design from supplied requirements and label choices as proposals; do not invent an audit.

Finish with the actual inputs, preserved elements, missing evidence and observable identity outcome.

## 2. Derive a direction without restarting discovery

Read [identity diagnosis and direction](references/identity-direction.md) for the matching branch. Use known audience, purpose, intended qualities and accepted references. Separate product facts and positioning from proposed visual interpretation.

When direction is unresolved, translate a reference's specific quality into an original compositional or material decision, then show why it serves this product. Do not copy a reference's identity or treat a named style as official brand specifications. Compare only alternatives that could change the decision; there is no fixed concept count, mandatory interview or repeated approval cycle.

Keep brand review distinct from task usability. Assess appropriate expression, hierarchy, recognition, coherence and actual deployment against the brief. Use confirmed relevant comparisons only when they help; do not invent competitors, numeric scores or a legal clearance claim.

Finish with a traceable direction and explicit status of the consequential choices.

## 3. Make the system concrete and inspectable

Document the necessary semantic color roles, type roles, spacing/composition, icon language, imagery treatment, motif and motion character at their existing owner. State none where an element is unnecessary. Record each important choice's purpose, source, accepted/proposed value, intended use and limits. Distinguish the fixed core from the flexible range.

Keep approved logo artwork and its optical variants with logo-design and its actual asset owner. Place the designated file and variant; do not redraw, recolor or re-proportion it while applying the system. Imagery specs and complex asset production use image-art-direction when appropriate; UI motion uses motion-design. Reuse the actual host capabilities rather than assuming those methods or a provider are installed.

For rendered or interactive acceptance, follow the configured visual-verification playbook and the user's preferred accessible environment; record any fallback and its evidence limits. Build a representative rendered application with real or explicitly labelled content before scaling the system. Compare meaningful contexts, such as a dense product view and a communication piece, when both are requested. Inspect typography, actual asset rendering, hierarchy, content fit and continuity. Covering the mark can reveal which other cues carry identity; it is a design probe, not proof of audience recognition.

Finish with inspectable system evidence. When rendering or required assets are unavailable, retain the independently useful specification, identify the exact gap and label the system unverified rather than claiming a finished kit.

## 4. Package reuse and complete requested applications

For repeated fixed-format pieces, read [collateral systems](references/collateral-system.md). Define reusable blocks and the slots allowed to vary; stress-test real long, short, dense and missing-content cases before a batch. Point to the canonical assets and decisions rather than maintaining copied masters.

Use native document, presentation, PDF, image or site capabilities for the requested outputs and inspect the final exports. Keep actual editing/export behavior and production requirements with that format workflow. A system proposal is not a shipped website, generated image, editable slide deck or press-ready PDF.

Carry out ready authorized applications in the same assignment; do not stop at guidelines when the user requested deliverables. Save durable decisions, asset provenance, source revision and checks at the existing owner. Distinguish proposed direction, accepted identity, implemented examples and verified distribution. Report only the tested contexts and preserve a concrete next check for any remaining gap.

Read [sources and adaptations](references/sources.md) when auditing or updating this method.
