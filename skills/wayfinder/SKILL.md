# Find a decision route

## 1. Name the destination

Follow the user's configured operating guide once per session and its active tool-call version. Reuse verified context; load the relevant project, current task and source owners, refreshing affected sources after material changes or uncertain writes. If required context is inaccessible, name the gap and continue only independently supported work. Use the routed context-entry playbook when available.

Use available agents without waiting for an explicit user request when this method calls for independent fact-finding or when a bounded parallel task or separate check would improve the result. Follow the routed delegation procedure; give each worker a source/revision, scope, allowed actions and expected evidence. Keep one writer per shared object, use the current host capabilities and let the parent verify and integrate the result. If delegation is unavailable, continue supported work and state any required independence that remains unproven.

Read the goal, accepted decisions, existing roadmap and evidence. Define what must become decidable before implementation can safely start. Retain established scope and explicit batch limits. If the direction is already settled, use plan-work or implement-spec instead of creating a discovery map.

Finish with a bounded destination, its existing owner and a distinction between facts to investigate and choices needing human judgment.

## 2. Map only real uncertainty

Use [decision records](references/decision-map.md). Reuse existing decision tasks; a map is a small index pointing to their evidence, not another copy. State questions that can already be phrased precisely and link their actual blockers. Keep later uncertainty coarse until prerequisites make it specific. Separate out-of-scope work from unresolved in-scope work.

For every proposed investigation state the result that would change the next action. Compare alternative routes only where a genuine choice remains; name the assumption and the cheapest observation that could reject it. A new abstract contract layer, document or ticket does not itself resolve uncertainty. Finish with a ready decision or investigation, explicit dependencies and no invented identifiers or silently assumed answer.

## 3. Resolve the ready question

Choose by accepted priority and prerequisites. Research facts with the research method when appropriate, make a bounded prototype for a question needing concrete behavior, and use domain-modeling for uncertain meaning. Load only the selected method. If unavailable, perform a supported bounded investigation and disclose the missing capability. Ask the user only for an unresolved consequential choice; never supply their answer or reopen a confirmed decision just to complete a template.

Delegate independent fact-finding or challenge under the standing authorization above. Work can be sequential when investigations share a prerequisite. Honor a user-defined one-batch boundary; otherwise there is no artificial one-ticket-per-session stop. Finish the question with evidence and a decision, a proposal awaiting a real choice, or a concrete blocker. Report which state actually applies.

## 4. Update the route and hand over

Record the answer once at its existing owner, preserving rationale, exact source/date and what could invalidate it. Update only the map's pointer and affected dependencies; preserve concurrent work. Verify writes. Continue ready authorized discovery until the scoped destination is clear or a material blocker remains.

The route is clear only when the required choices have evidence/authority and the next delivery step is executable. A blocked route is not resolved. Hand settled work to plan-work or implement-spec under existing authorization; discovery alone grants no product, migration, publication or scheduling permission.
