# Design motion that follows user intent

## 1. Pin the behavior and visual job

Follow the configured operating guide once per session, accepted method route and existing product/task owner. Reuse the actual build, design system, accepted choices and supplied examples. Identify whether the request is a proposal, prototype or authorized product change; a motion brief alone grants no implementation or publication authority.

State the user action, object affected, initial state, meaningful change and stable resulting state. Distinguish immediate functional feedback, spatial orientation and optional expressive movement. Keep business state, focus and accessibility semantics owned by the actual product logic. Do not delay a committed action just to complete decorative choreography.

Use visual-storytelling for a timed narrative or encoded film and the existing logo owner for a new mark. A precise settled transition or small repair needs no full motion workshop. Missing runtime or product evidence limits dependent claims, not independently useful specification work.

Finish with a bounded behavior contract and observable acceptance.

## 2. Choose a coherent motion model

Read [interaction contracts](references/interaction-contracts.md) for triggers, continuity, interruption and reduced motion. Define what moves, why, its origin/destination, hierarchy, timing character and which properties stay fixed. Use the established identity; expressive amplitude and repetition should fit frequency of use and attention cost.

Distinguish time-triggered, scroll-progress-driven and direct-manipulation behavior. Preserve state when input reverses, repeats, cancels or seeks. Prefer one clear state/timeline owner over independent timers competing for the same object. Keep essential cues in the reduced-motion or static route and honor preference changes during a session.

Compare concrete motion studies only when they resolve an unsettled decision. Inspect the actual moving result rather than selecting from prose or static frames alone. No fixed animation count, easing formula, duration, library or mandatory approval round applies to every interface.

Finish with entry, active, interrupted and final states, including a usable fallback.

## 3. Build the authorized slice

Read [implementation branches](references/implementation-branches.md) for the actual platform and [spatial scenes](references/spatial-scenes.md) only for canvas/WebGL/3D. Check the installed platform/library version and current primary documentation before relying on version-sensitive APIs. Prefer the existing stack and smallest capability that implements the required behavior; no automatic framework installation.

For a substantive code change, load evidence-driven-development and its review owner. This method owns motion behavior and craft, not a second development lifecycle. Use the configured delegation procedure early for useful independent behavior analysis, source work or review; assign one controller to a shared live surface. Integrate workers against the actual resulting candidate.

Keep layout/state ownership explicit. Clean up listeners, observers, timelines and animation resources on unmount or mode changes; do not stop unrelated application animation globally. Avoid per-frame application re-renders when a suitable animation value or native mechanism can own visual interpolation. Let measured constraints, content and accessibility determine optimization.

Finish with a usable slice or inspectable proposal, labelled according to what was actually built.

## 4. Verify the real response

Follow the configured visual-verification playbook and the user's preferred accessible environment. Discover the target runtime before using a cloud preview; a local runner failure requires checking relevant available alternatives. For a distinct real interaction journey, load test-user-flows. Static frames, metadata probes and source review prove different things from exercised controls or measured playback.

Inspect starting, intermediate and final states, at representative content density and relevant window sizes. Exercise repeated activation, reversal, cancellation, direct entry/seek, navigation/remount and reduced motion where relevant. Confirm that the depicted subject or selected item actually changes as promised, not just its label. Check focus, reading order, keyboard control, loading/failure behavior and semantic visibility independently of the animation.

Measure performance only on an identified runtime/workload; do not infer a frame-rate claim from transform/opacity use or a target setting. Repair concrete failures and repeat affected checks. If capture or input is unavailable, retain the untested boundary and continue only supported observations.

## 5. Deliver and retain the owner

Deliver the actual proposal, implementation or requested export, with the behavior contract and evidence at the existing owner. Record build, surface, actions and observed results, including reduced-motion and interruption coverage. A prototype does not prove production integration; an image does not prove animation. Keep unresolved acceptance visible rather than claiming universal visual or accessibility success.

Read [sources and adaptations](references/sources.md) when maintaining this method.
