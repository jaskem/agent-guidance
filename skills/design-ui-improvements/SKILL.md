# Design UI improvements

## 1. Ground the proposal

Follow the configured operating guide once per session and its active tool-call version. Read the relevant project/task owner and supplied findings; reuse verified context and refresh material changes. Identify the affected task, actual baseline, product constraints and design system. Carry evidence limits forward; a missing source limits only dependent claims. Without a baseline, use supplied requirements for an explicitly proposed design and record the missing comparison; route an unknown-interface audit to audit-ui-ux.

Finish with a bounded objective, traceable input findings and behavior/information to preserve. The method does not authorize changing the app.

Classify the work as an extension, an improvement preserving identity, or an authorized overhaul. Identify the behavior, information and integration contracts that must survive. For a new experience, distinguish supplied requirements from proposed choices and retain the absent baseline as an evidence limit.

Use available agents on your own initiative when this method calls for separate work or when bounded independent work or review would improve the result; no explicit user request is needed. Follow the routed delegation rules. Give each worker the relevant source, question, allowed actions, owned objects and expected evidence; keep one writer per shared object and verify the combined result in the parent. Use the actual host capabilities and model/fork rules. If agents are unavailable, continue supported work without claiming an independent review.

## 2. Choose the smallest useful direction

Map each priority finding to a concrete change. Reuse product vocabulary and established visual language. Change hierarchy, grouping, disclosure or feedback to support the task. Preserve necessary expert controls and data.

Use [art direction](references/art-direction.md) when visual language, density, motion, assets or identity fidelity needs a consequential choice. Make those choices affect the proposal; an already-decided repair needs no separate style exercise.

For a consequential unresolved choice, compare meaningful alternatives and trade-offs. Recommend with reasons; leave domain decisions needing input open while completing independent proposals. Use an existing prototype method only when interaction or state uncertainty needs an executable experiment.

Finish when every proposed change addresses an input finding or supplied requirement and has a task-based reason.

## 3. Make the change inspectable

Use [visual handoff](references/visual-handoff.md) for before/after views, component details and tokens. Work at a stated viewport and representative density. Keep observations, annotations and proposed interfaces visibly distinct.

Show surrounding app context to judge hierarchy, plus readable details where needed. Exact geometry belongs in HTML/SVG or document drawing tools. Inspect rendered output and correct clipping, tiny labels, missing assets and inconsistent state cues. If rendering is unavailable, label the artifact an unverified draft and retain the rendering check.

Finish with a viewable artifact or explicit rendering limit, not a prose promise of a redesign.

## 4. Define acceptance and sequence

State what must remain true, what users should see/do differently and how it will be checked. Separate visual acceptance from interaction, accessibility, performance and usability validation. Screenshots verify layout in captured states; use test-user-flows for real interactions and the applicable assessment for security or performance claims. A proposal is not proof of implemented behavior.

Group changes into the smallest coherent delivery slices. Use existing tasks and dependencies; record proposed work at the established tracker without treating recommendations as accepted implementation. Keep uncertain assumptions as validation work.

Finish with a visual improvement plan whose proposals, dependencies, checks and open decisions are clear. Link the baseline, output and owning tasks. Report the artifact inspected and untested states.

When the user also requests a build, carry the chosen design and acceptance into the appropriate authorized host implementation route. Do not stop at a proposal when implementation is part of the assignment; keep proposed, implemented and observed behavior distinct.
