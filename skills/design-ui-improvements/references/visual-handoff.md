# Visual handoff

For each proposal include finding ID, task, baseline crop/reference, proposed view, reason and acceptance. Label mockups as proposals with date/version. A drawing is not a captured working app.

Compare at the same scale or disclose the difference. Use realistic long names and dense data as well as empty states. Retain native language/units. Provide overview and enlarged detail rather than squeezing everything onto one page.

Define only tokens needed by the change: surfaces, primary/muted text, interactive accent, selection/focus and status colors; type roles, spacing and component sizes. Reserve semantic colors for consistent meanings, including non-color state cues. Proposed values remain provisional until rendered contrast and target-platform scaling are verified.

For structured data, show headers with realistic values and explain the affected width, header/value alignment, wrapping, truncation/full-value access and resizing or scrolling choices. Distinguish text, comparable quantities, identifiers and dates; no universal column width or minimum font recipe replaces rendered inspection. Check long labels without stray-letter breaks and preserve useful expert density.

Describe changed interactions through starting state, action, result, cancellation and recovery. A static proposal cannot demonstrate them. Retain labels and keyboard paths for implementation inspection.

Include sequences in which a second edit, automatic result or refresh could replace earlier input. Specify which choices remain valid, which domain dependencies invalidate them, and how that is communicated and recovered. Improve task order, labels and contextual feedback before adding instructions; retain necessary help.

Changes to labels, type, padding or widths require renewed inspection of the affected final proposal states. A prior capture does not establish the revised fit.

Resolve grouping/layout before component polish. Map delivery slices to evidence and acceptance. Unseen dialogs, physical DPI, assistive technology and user testing stay explicit coverage gaps.

Carry component state and semantics into the handoff: accessible name, keyboard activation, focus entry/return, selection and error feedback. Use the existing component/design vocabulary and central state owner. Avoid framework, file-size, spacing or breakpoint mandates copied from unrelated examples; choose values and checks that fit this product's actual platform and density.
