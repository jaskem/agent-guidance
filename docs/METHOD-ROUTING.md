# Task methods and specialist roles

This router owns selection, not a second implementation of each method. Read the consumer's current instructions and accepted scope first. Load only the selected method body and materially relevant roles. Installed, enabled and actually read are different states. A method never adds permission to implement, publish or schedule.

## Establish configured context

Follow the user's configured operating guide at the start of a session, then the relevant project home and current task owner. Use the selected [context-entry playbook](../guidance/playbooks/context-entry.md) through the consumer's local route; this central link does not override a pin. Reuse verified context until the project, scope or material facts change. A general question needs no project scan. If a required source is unavailable, disclose the access gap and pause only dependent work; do not report a remembered source as freshly read.

Small factual questions and editorial changes need no full workflow. A clear implementation task does not first require an interview. A planning-only request remains planning-only. A large authorized implementation continues through its work packages; neither a new session nor creating an issue is a reason to stop by itself.

The [coherent skillset](SKILLSET.md) and its [single catalog](../skills/catalog.json) own the 24 active procedures. Relevant techniques from the four provider suites are integrated into these packages and their directly linked references. Use the canonical method rather than appending a competing provider lifecycle. An explicitly requested provider remains a distinct user choice; provider files and invocation metadata are not rewritten.

Select by the requested result. `wayfinder` resolves a direction that is not yet clear; `plan-work` turns a sufficiently clear direction into executable scope; `implement-spec` sequences an already authorized task graph; `evidence-driven-development` executes one substantive change. `triage` owns intake coverage and delegates bounded diagnosis rather than duplicating it. `research` supplies a decision brief using the existing research-verification criteria. `to-questionnaire` prepares a draft, never sends it by implication. Architecture proposals remain proposals until implementation is authorized.

All catalog methods except the explicitly requested grill-me permit implicit selection for their discriminating descriptions. This is permission to choose a relevant method within the request, not to start unrelated scans or background work. Existing project and tracker owners remain authoritative. Personal/Notion registration and saved package verification are separate from this router; current client registries can be cached.

`evidence-driven-development` declares `code-review` as a required method in the skill catalog. Resolve the installed version against its distribution record. If unavailable, read the pinned canonical source recorded there; if that source cannot be reached, report the dependent review as incomplete and continue independent work. Other methods are selected as needed, not a mandatory dependency chain.

## Preserve local ownership

Follow the existing product plan, terminology, task tracker, decision records and closure workflow. Ownership is project-specific: code may live in a repository while Notion owns tasks and decisions. Resolve each owner separately. A navigation page can link to those sources and give a dated summary; it cannot silently become a second task or product-contract owner. Preserve the distinction between proposed, accepted, implemented, checked and published.

Research, recovery, closure and instruction feedback already have [playbook owners](../guidance/catalog.json). Load the applicable procedure through the consumer route rather than inventing another. Package-specific steps should invoke that role or procedure when available; their self-contained task steps must retain safe handling when a host lacks it.

Choose available subagents autonomously when the selected method asks for them or independent research, execution or verification materially helps the task. The user does not need to mention agents or repeat permission merely for delegation. Preserve the task's actual authority and tool limits. Before delegating, follow the selected [delegation playbook](../guidance/playbooks/delegation.md) through the consumer's local route. If unavailable, retain bounded assignments, non-overlapping writes, explicit evidence and parent verification. Availability of several roles is not authorization to create a standing agent team. A skill call is not a separate agent; a separate agent sharing the author's context is not a fresh-context review. Choose delegation for independent useful work or material review value, not role count or task size alone.


## Compose by result

Use one primary procedure and only the necessary specialist work. Domain identity stays with domain-modeling; public caller behavior belongs to design-interfaces. UI audit judges usability; test-user-flows establishes observed runtime behavior. A security assessment or performance investigation is bounded and does not silently become a product rewrite. prepare-release follows the actual desktop, shared-folder or service distribution. write-content selects the requested writing phase without an obligatory series.

For documents, spreadsheets, presentations, images and connected services, use the host's required artifact/app capability as appropriate. Those are execution capabilities alongside this set, not duplicate methods to import into the Notion collection. A simple question or short edit can be answered directly.
