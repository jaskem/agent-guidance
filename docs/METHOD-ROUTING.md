# Task methods and specialist roles

This router owns selection. The [work cycle](../guidance/playbooks/work-cycle.md) owns general execution, result-specific evidence and closure; methods own their bounded procedures. A role supplies a perspective and a tool supplies capability. None adds authority to implement, publish, send or schedule.

## Establish configured context

Start from the user's single configured operating guide once per session. Follow its conditional context route for a standalone object or a known project; a general question requires no project scan. Resolve the actual source and task/document owners using [context-entry](../guidance/playbooks/context-entry.md), preserving the consumer's pinned route. This central pointer does not upgrade a consumer.

Select from the [catalog](../skills/catalog.json), resolve the accepted distribution/version, and actually load the selected method plus necessary references. Installed, enabled, read, applied and verified are distinct states. If installed copies disagree, compare the canonical source, accepted pin and distribution evidence; modification time alone does not decide precedence. Pause only work dependent on an unresolved source or access gap.

For substantive work, establish the work-cycle route before execution: result, actually loaded primary method/source, triggered conditional methods, intended observation surface and useful independent assignments. Follow the catalog's conditional routes and accepted external reference supplements only when their trigger is present, loading the target before its dependent technical decision. When work changes, re-evaluate the affected route. At closure, reconcile applied methods, decisions/checks, integrated agents and observed evidence at the existing work owner. A missing required branch remains an explicit gap; a checked box is not proof of application.

## Compose without duplicate workflows

1. Use direct handling for a simple answer or small edit. For substantial work choose the method for the requested end result, load it and preserve already accepted decisions.
2. Resolve a decisive knowledge gap with bounded research, diagnosis or a prototype. Return to the original objective after that sub-result; do not stop at research when execution is authorized.
3. Compose only necessary outputs. For example, a decision memo can use research then write-content; an approved software plan can use implement-spec and an authorized release step. Dependencies determine order, not the number of available methods.
4. Resumption identifies the next action; scheduling changes when work will run. Neither replaces the underlying content route. A method never confers new authorization.
5. Keep distinct owners: constraints establish what must hold; CI/CD establishes where checks run and whether failures block; code-review assesses the actual change; prepare-release verifies delivery. Existing checks can simply run without any new constraint or pipeline project.
6. Use observability for lasting signals, not every bug diagnosis; use migration for supported consumers/data transitions, not every refactor. Their software changes still use the applicable implementation and review procedure.

For metered software verification, use the work-cycle safeguards before starting CI. For a cost or pipeline-selection decision, consult the optional [CI efficiency reference](../guidance/resources/ci-efficiency.md) when available. Existing methods and project requirements retain ownership; no extra audit or skill is required for ordinary test execution.

All catalog methods permit implicit relevant selection except grill-me, which remains explicit. Design output uses the relevant owner: UI proposals use design-ui-improvements; existing-interface assessment uses audit-ui-ux; complex raster series use image-art-direction; designed HTML/web/video narratives use visual-storytelling; reusable identity systems use design-brand-system; interactive transitions use motion-design. Simple image requests use the native image capability directly, and native documents/slides keep their format capability. None of these changes the source of product facts.

The accepted external method `logo-design` owns logo identity, concepts, mark construction and logo kits. Resolve its personal extension and accepted distribution from the configured guide; do not substitute the upstream package and overwrite custom work. It is registered separately in the catalog because this repository does not own its source. A settled logo applied to a brand system or film needs its approved asset, not another logo-design lifecycle. Missing logo access blocks only that dependent result.

The accepted external method `modern-web-guidance` supplies GoogleChrome web-platform guidance for HTML, CSS, browser APIs and client-side JavaScript. Resolve the accepted self-contained online adapter from the configured distribution record and load it before the dependent technical decision. Search focused capabilities, read relevant guides, apply the actual browser/runtime policy, and check resulting choices. This router owns the shared reference trigger declared under the external method in the catalog. Load it alongside the selected procedure, including when that procedure is already active; the procedure remains the execution owner. It is not another design/development lifecycle. The [integration record](MODERN-WEB-GUIDANCE-2026-11-21.md) records provenance, intentional adaptations and evidence limits.

| Branch | When to load modern-web-guidance | Existing owner retained |
| --- | --- | --- |
| Implementation, bug diagnosis or prototype | HTML/CSS/browser APIs/client-side behavior is changed | evidence-driven-development or prototype; implement-spec reaches it through its implementation dependency |
| UI design, audit, web narrative or motion | Technical web patterns or browser fallbacks affect the result | design-ui-improvements, audit-ui-ux, visual-storytelling or motion-design |
| Review, security or performance | Actual browser semantics, security or measured web bottlenecks are assessed | code-review, review-security or optimize-performance |
| User-flow verification | Browser semantics or compatibility criteria need clarification | test-user-flows and the selected visual-verification environment |
| Backend/native-only work, CI, wording or static brand/image work | Do not load for these alone | Original direct/task route |

Do not perform a broad legacy scan for a bounded UI change. Preserve compactness, established design, supported browser fallbacks and actual target-runtime checks. Guide retrieval is source evidence, not visual or interaction acceptance. The online adapter retrieves only selected full guides from their official pinned source. It needs source-retrieval access, with current official documentation as a disclosed fallback; it includes no offline corpus or npm CLI. No automatic package update, additional approval round or mandatory skill footer is introduced.

An unrelated installed provider is not a second default lifecycle. A provider explicitly requested by the user remains available within its real scope. Provider files are not rewritten.

evidence-driven-development routes to code-review when an actual code change is made. Diagnosis without a code change has no change-review dependency: verify its evidence through the work cycle, with independent assessment when useful, without inventing a diff or comparison baseline. implement-spec retains both required dependencies for actual implementation, as declared in the catalog. Resolve unavailable dependencies against the accepted canonical release. If that source is inaccessible, name the dependent gap and continue independent work. Other methods are conditional sub-results rather than a mandatory chain.

The package validator checks required dependencies and declared conditional targets for valid names, triggers and disclosure in the owning package. It also checks every primary selection entry. These checks can reject structural drift in CI; they cannot observe whether a host loaded a method or an agent followed it. Actual route evidence and behavioral trials address those separate questions.

## Use the appropriate host capability

The method catalog is not a list of every tool. Use the host's required artifact, service or scheduling capability alongside the general cycle, loading its instructions when applicable.

| Result | Handling and finish |
| --- | --- |
| Short answer, summary or minor wording change | Direct handling and proportionate source check; no project/task ceremony |
| Document, report or presentation | write-content when substantial composition is needed, plus the format capability; check content and final rendering, save at the intended destination |
| Spreadsheet, analysis or conversion | Data capability; verify input identity, units, formulas/counts and material edge cases; produce usable saved output |
| Image, diagram or visual design | Appropriate creation/design capability; inspect the result; use exact diagram/plot tools for factual structures and measurements |
| Review of a document, analysis or proposal | Relevant content/data criteria and host capability; report findings against supplied requirements; no code-review or unsolicited edit |
| External app update or send | Resolve exact account/object/recipient and authority; refresh shared target before mutation; system evidence distinguishes draft, saved and sent |
| Later, recurring or conditional task | Actual scheduling capability; verify trigger, timezone, scope and output destination, inspect uncertain creation before retry; no background-agent promise |
| Simple explanation or learning | Direct explanation; teach for a useful bounded lesson, without forcing a quiz or code context |

A scheduler request is not CI/CD merely because both mention automation. Explicit publication or sending can be part of the authorized goal; drafting alone does not authorize either. A status question during work receives a brief answer and the authorized objective continues.

For visual or interactive acceptance, follow the selected [visual-verification playbook](../guidance/playbooks/visual-verification.md). Discover the actual target and configured environment before choosing a cloud browser. Prefer a relevant accessible user-selected remote desktop; preserve the tool's interaction rules and record the reason and evidence boundary of a fallback. One failed local browser launch is not proof that all rendering paths are unavailable.

## Preserve local ownership

Follow the existing product plan, terminology, task tracker, decision records and closure workflow. Ownership is project-specific: code may live in a repository while Notion owns tasks and decisions. Resolve each owner separately. A navigation page can link to those sources and give a dated summary; it cannot silently become a second task or product-contract owner. Preserve the distinction between proposed, accepted, implemented, checked and published.

For a user-authorized continuous-improvement run or a real reusable failure/skill gap, use maintain-agent-instructions with the selected instruction-feedback-loop playbook. It owns capture, cause, candidate, comparison, review, bounded activation and recovery. Check existing coverage before searching or adding a skill. Periodic work needs a registered scheduler; current setup/user authority and consumer pins remain separate.

Research, recovery, closure and instruction feedback already have [playbook owners](../guidance/catalog.json). Load the applicable procedure through the consumer route rather than inventing another. Package-specific steps should invoke that role or procedure when available; their self-contained task steps must retain safe handling when a host lacks it.

Choose available subagents autonomously when the selected method asks for them or independent research, execution or verification materially helps the task. The user does not need to mention agents or repeat permission merely for delegation. Preserve the task's actual authority and tool limits. Before delegating, follow the selected [delegation playbook](../guidance/playbooks/delegation.md) through the consumer's local route. If unavailable, retain bounded assignments, non-overlapping writes, explicit evidence and parent verification. Availability of several roles is not authorization to create a standing agent team. A skill call is not a separate agent; a separate agent sharing the author's context is not a fresh-context review. Choose delegation for independent useful work or material review value, not role count or task size alone.
