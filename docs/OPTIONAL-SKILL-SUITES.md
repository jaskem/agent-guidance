# Optional skill suites

This router composes installed provider skills with the existing task methods. It does not install a provider, override its ownership, migrate a tracker or add a mandatory development lifecycle. Provider availability and reviewed versions belong in the user's distribution record; inspect the actual registry before using a name.

## Select the requested result

1. Follow configured context entry. A standalone question does not need a project; resolve a project only when its facts or output destination matter.
2. Choose one primary workflow from [METHOD-ROUTING.md](METHOD-ROUTING.md). For an explicitly named plugin or skill, use that intended workflow and retain its namespace. Resolve an ambiguous name from the user's request and verified availability.
3. Load a specialist only when its omission could materially affect correctness, usability, security, performance or delivery. Read its actual body and the references needed by this task; listing it is not applying it. Do not load the whole suite as a checklist.
4. Reconcile constraints before acting. Current user scope, project contracts and tool policies remain authoritative. A vendor's example is not a new product requirement, quality threshold, library choice or permission. Explain a material conflict and preserve the authorized goal rather than silently lowering acceptance.
5. Record which method and material specialist were consumed at the existing work record when one exists. Simple chats need no extra administration. Validate the outcome at its actual boundary; a skill name, static review or another project's benchmark is not product evidence.

## Existing workflow owners

Use personal task methods as the default where they are already the configured route. A namespace distinguishes a separately selected provider workflow from a duplicate installation. If a personal package is also available through Notion, load one verified copy.

For a document, spreadsheet, presentation, image, browser action or connected service, use the appropriate artifact/service workflow and available tools. Those may be the primary route for that result; this composition does not displace host-required capabilities or turn every artifact into a repository task. Preserve the user's chosen app and output destination.

| Result | Primary owner | Optional provider depth |
| --- | --- | --- |
| Explain, research or answer | Normal answer, research or teach | Relevant documentation/learning techniques; no coding ceremony for ordinary questions |
| Resolve uncertain direction | wayfinder, domain-modeling, plan-work | idea-refine, API/interface design, bounded independent scrutiny |
| Authorized multi-task delivery | implement-spec | incremental implementation, selected migration/CI/release detail |
| One change or diagnosis | evidence-driven-development | debugging, testing, frontend, source verification and relevant technical disciplines |
| Review a fixed change | code-review | Security, performance, accessibility and optional complexity review |
| Inspect existing architecture | improve-codebase-architecture | codebase-design and measured simplification alternatives |
| UI audit or proposal | audit-ui-ux, design-ui-improvements, prototype | frontend implementation/accessibility and runtime browser evidence when appropriate |
| Context, instructions or handoff | maintain-project-context, maintain-agent-instructions, handoff | context-engineering, documentation and agent-writing references |

## Matt Pocock provider

The `mattpocock-skills:` bundle is a distinct implementation from the configured personal adaptations. Retain explicit-only invocation where its actual metadata requires it. Suggest such a command when useful; do not secretly invoke an explicit-only wrapper through another skill. If the user explicitly selects it, inspect its packaged dependencies and adapt only within current user/project/tool authority.

- Existing personal methods already own implementation, review, diagnosis, domains, prototypes, research, architecture, planning, triage, handoff and teaching by default. Do not run both provider and personal versions in sequence just because both exist.
- `ask-matt` is an explicit chooser. A scratch current directory does not establish a durable project. Resolve project identity, source and destination first.
- `grill-me`, `grill-with-docs` and `grilling` are useful for requested design interviews. An established decision or delegated ordinary judgment is not missing consent. Keep accepted answers and actual decision owners.
- `loop-me` can specify an actual repeated process. Designing a process does not activate a schedule or authorize reading new sources.
- `writing-fragments`, `writing-beats` and `writing-shape` add useful non-code writing phases. Use the requested phase and authorized document destination; avoid an unsolicited three-stage writing workflow.
- `wait-what` can re-explain an unclear answer; a direct simple rephrasing rarely needs a new artifact or course.
- `to-questionnaire`, `to-spec` and `to-tickets` are useful explicitly selected output workflows. Preserve already established facts and planning/task owners; no parallel local tracker.
- `resolving-merge-conflicts` supplies conflict techniques. Preserve original changes and conflict state; never interpret generic “stage everything” or “never abort” language as authority to overwrite or publish unrelated work.
- `setup-matt-pocock-skills`, `setup-pre-commit` and `setup-ts-deep-modules` change project tooling. Use only for a requested setup with matching stack and verified scope. Existing CI and project routers remain authoritative.
- `git-guardrails-claude-code`, `claude-handoff`, `migrate-to-shoehorn`, `scaffold-exercises` and `wizard` require specific runtime/tooling or document structures. Establish those before selection; do not install a CLI, hooks or a new test framework merely because the skill references one.
- `tdd`, `codebase-design` and `writing-for-agents` can be targeted references. Interface vocabulary, test choices and clarity matter; fixed jargon substitutions or obligatory confirmation at every test boundary are not new user requirements.

## Ponytail

Use `engineering-suite-ponytail:entry-ponytail` when that plugin is selected, then its own internal dependency. Prefer an explicitly bounded simplicity pass or one-shot review over a persistent mode. Keep actual skill mode state explicit; this router does not enable full/ultra across sessions.

- `ponytail` supplies YAGNI, existing platform features and standard-library alternatives when coding. Readable behavior-preserving simplicity is the goal; shortest diff, one-line code or fewer files alone are not success criteria.
- `code-simplification` can be a clarity aid. Verify error timing, return types and representations before applying an illustrative rewrite.
- `ponytail-review` inspects a fixed diff for complexity; `ponytail-audit` inspects a requested repository scope. In a bundle whose review excludes correctness/security/performance, its conclusion cannot authorize shipping.
- `ponytail-debt` inventories actual markers; no markers does not mean no technical debt. Keep actionable follow-up at the existing tracker.
- `ponytail-help` explains the installed bundle. `ponytail-gain` describes vendor benchmark claims; report their source/limits and never present them as measurements of the user's projects.

## Superpowers

The `superpowers:` bundle provides a coherent alternative engineering lifecycle. Select its useful techniques within the current task; do not stack that entire lifecycle on top of the configured personal methods.

- `brainstorming` and `writing-plans` can deepen genuinely unresolved design and planning. Reuse accepted decisions, existing specifications and the actual task owner. A clear authorized change or small question does not need a new design approval cycle or a parallel local plan.
- `systematic-debugging`, `test-driven-development` and `verification-before-completion` add hypothesis discipline, distinguishing regressions and evidence before claims. Apply checks appropriate to the change, preserve valid evidence from the same revision and boundary, and do not confuse repeated commands with stronger proof.
- `dispatching-parallel-agents` and `subagent-driven-development` help with independent bounded work and review. Retain the configured delegation rules, one writer per shared object, precise handoffs and parent integration. Skill availability does not require one agent per task, a different model or a fabricated fresh-context review.
- `executing-plans` follows an authorized task graph and actual dependencies. A review-loop limit or documented ruling does not itself satisfy an unmet product criterion; keep unresolved required acceptance open.
- `requesting-code-review` and `receiving-code-review` support evidence-based review. Keep the fixed comparison, source requirements and existing review owner; assess feedback before changing code.
- `using-git-worktrees` and `finishing-a-development-branch` apply when isolation or integration is needed. Inspect existing work and the actual runtime first. A worktree fallback, menu choice or generic cleanup recipe cannot authorize deleting unrelated changes, a branch or a checkout.
- `writing-skills` and `diagnosing-superpowers` can investigate a concrete method defect. Maintain the canonical owner and test discriminating cases; access to a session does not authorize exporting its transcript or sending a report upstream.
- `using-superpowers` is the bundle entry, not a replacement for the user's operating guide. Its broad invocation threshold and lifecycle defaults do not make every small chat a development process. Follow current user, project and host authority when their requirements differ.

## Reconcile conflicts and capabilities

Preserve existing tests and quality floors. Do not weaken checks to get green, but do not treat every example threshold or unchecked helper script as an established project gate. A legitimate change to a quality constraint needs visible justification and the project's actual authority.

Local desktop, file-share, library and service environments require different acceptance. Hardware, shared-folder behavior, real browser flows and deployment must be observed at their actual boundary; static skills and fixtures do not establish that acceptance.

For missing tools or references, state the unavailable capability and continue independent supported work. Read a matching executor bundle's references only after confirming the source/version or main content matches; do not silently substitute a newer upstream. Do not alter plugin-owned files, disable installed skills or change permissions under the guise of routing.

Human involvement is for a material unresolved choice or actual authority boundary. Reuse accepted scope and standing authorization. Ordinary reversible implementation choices and already authorized writes need no extra vendor-imposed approval ceremony. Tool access and safety policies still apply.
